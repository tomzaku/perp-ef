**Read committed** is the weakest isolation level you'll meet in practice — and the *default* in Postgres, Oracle, and SQL Server. It makes exactly two promises:

**1. No dirty reads** — you never see another transaction's *uncommitted* data.

Why it matters: transaction T1 debits Alice $100 but hasn't yet credited Bob. If T2 could read Alice's new balance now, it would observe money that has vanished from the system. Worse, T1 might *abort* — T2 acted on data that never existed.

**2. No dirty writes** — you never *overwrite* another transaction's uncommitted data.

Why it matters: two transactions each write two rows (say, a car sale updates `listings.buyer` and `invoices.recipient`). Interleaved dirty writes could leave the listing saying "sold to Alice" and the invoice billing Bob.

**How it's implemented:**
- Dirty writes → **row-level locks**: a transaction wanting to write a row must acquire its lock and holds it until commit/abort. The second writer simply waits.
- Dirty reads → *not* with locks (readers blocking on writers would be slow). Instead the database keeps **two versions** of each row: the committed old value (served to readers) and the uncommitted new value (visible only to the writer). At commit, readers switch to the new value.

**What it does NOT prevent:** each *statement* sees the latest committed data, so two reads within one transaction can see *different* states — **read skew**. And read-then-write races (**lost updates**) sail right through.

Explain read committed's guarantees, implementation, and its famous failure mode.

## Solution

```js
// ════════════════════════════════════════════
// Guarantee 1: no dirty reads (via row versioning)
// ════════════════════════════════════════════
// Row 'Alice' during T1's uncommitted debit:
//   committed value:   { balance: 500 }   ← what readers see
//   uncommitted (T1):  { balance: 400 }   ← only T1 sees this
// T1 commits → committed value becomes 400 atomically.

// ════════════════════════════════════════════
// Guarantee 2: no dirty writes (via row locks)
// ════════════════════════════════════════════
// T1: UPDATE listings SET buyer='Alice' WHERE id=7;
//        → T1 holds row 7's write lock until commit
// T2: UPDATE listings SET buyer='Bob'   WHERE id=7;
//        → BLOCKS until T1 commits, then applies on top.
// No interleaved half-updates across rows.

// ════════════════════════════════════════════
// THE FAILURE MODE: read skew (non-repeatable read)
// ════════════════════════════════════════════
// Alice has $1000 split across two accounts, $500 each.
// A transfer of $100 runs WHILE she loads her banking page:

//                      checking      savings
//   page reads checking:  500
//   transfer txn:          -100  →   +100     COMMITs
//   page reads savings:               500   ← pre-transfer value? NO:
//                                     600? NO — she sees 500 + 400=900
//
// Timeline that bites:
//   1. Page reads savings   = 500   (before transfer)
//   2. Transfer commits: checking 600, savings 400
//   3. Page reads checking  = 600?? or reads savings after...
//   → Depending on order she can observe $900 or $1100 TOTAL.
// Each individual read WAS committed data. The COMBINATION
// never existed at any point in time.

// ════════════════════════════════════════════
// Also unprotected: the lost update
// ════════════════════════════════════════════
// let likes = await db.query('SELECT likes FROM posts WHERE id=1'); // 10
// await db.query('UPDATE posts SET likes = ?', [likes + 1]);        // 11
// Two concurrent runs → both read 10, both write 11. One lost.
//
// Fixes available even at read committed:
//   UPDATE posts SET likes = likes + 1 WHERE id=1;   -- atomic write
//   SELECT ... FOR UPDATE;                           -- explicit lock
```

## Explanation

The two guarantees split neatly by mechanism, and interviewers like hearing that split articulated: **writes block writes** (row locks — cheap because write-write conflicts on the same row are rare), but **reads never block, and are never blocked** (old-value versioning — critical because *everything* reads, and one long analytics query holding read locks would freeze all writes).

The failure mode to internalize is **read skew**: within one transaction, statement #1 and statement #2 each see the *latest committed* state — but commits land between them, so they see *different* states. For a quick web request updating one row, who cares. But it's fatal for:

- **Multi-read consistency**: the bank-balance example — Alice's total appears wrong by $100.
- **Backups**: a backup walks the whole table over hours; parts reflect old data, parts new. Restoring makes the inconsistency *permanent*.
- **Analytics**: a `SUM(balance)` scanning rows mid-transfer double-counts or misses money.

The pattern of this whole chapter, previewed here: each isolation level is defined by **which anomalies it kills and what that costs**. Read committed kills dirty reads/writes for nearly free — which is exactly why it's the default. Killing read skew requires each transaction to see a frozen, consistent snapshot — **snapshot isolation**, the next lesson, built by extending "keep two versions" into "keep *many* versions" (MVCC).

## ELI5

The rule of read committed: **you only see finished work, never drafts.**

A friend is writing a two-part story. You can never peek at her rough draft (no dirty reads) — you only read chapters she has officially published. And two authors can't scribble on the same page at once — the second one waits (no dirty writes, via the row lock).

But here's the sneaky bug. You read Chapter 1 on Monday. On Tuesday she publishes a revision that changes *both* chapters. On Wednesday you read Chapter 2 — the *new* Chapter 2. Every page you read was "officially published," yet the story you experienced — old Chapter 1 plus new Chapter 2 — **was never a real book**. Chapter 2 mentions a character who, in your Chapter 1, hasn't been born.

That's read skew: each glance is legitimate, but glances at different moments stitch together a world that never existed. The fix in the next lesson: hand every reader a complete photocopy of the book *as it existed the moment they walked in*.
